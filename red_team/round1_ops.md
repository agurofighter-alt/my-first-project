# Round 1 — 壺割り所見(レンズ:運用・実装)

- 対象: rules.md v1.2(憲法)+ pot_A 実走1ラウンド(Stage0〜Stage3収束、Stage4待ち)
- 検証手段: 全ファイル精読 + git全履歴の突合(存在しないファイルは「一度も存在しなかった」ことまで確認済み)
- 凡例: 壊=型が主目的を果たせない致命傷 / 歪=目的からズレていく構造欠陥 / 軋=スケール・運用で詰まる摩擦

---

### RT1-OPS-1 [壊] task_XX.md は一度も実在せず、ファイル契約が丸ごと空洞
- 指摘: §6/§10/§12 が定める `task_XX.md` が pot_A にも git 全履歴にも一度も存在しない。蟲師への実入力(担当レンズ・バッチ指示・Stage2/3のゲート指示・例示)はすべて揮発プロンプトで運ばれ、記録が残っていない。
- 根拠: rules.md §12「各蟲師に渡すのは **`shared_context.md` の中身 + その `task_XX.md` の中身 + 出力フォーマット** だけ」、§10表「`task_XX.md`|個別・使い捨て|各蟲師への個別タスク」。`git log --all --diff-filter=A` に task ファイルの追加記録なし。progress_stage2_B.md「近傍変種: あり(**プロンプト例示どおり**)」——プロンプトに実質的内容(変種の例示)があった痕跡だけが残り、中身は失われた。
- 攻撃シナリオ: この壺の主目的(§13)は「蟲師の最小判断単位」の**測定**なのに、実験の独立変数=実際に渡した入力セットが未記録。state.md の「最小判断単位 = 確定」は誰にも検証も再現もできない主張になる。密閉(§12「含めない=密閉」)はプロンプト規律だけで担保され事後監査が不可能——キルログや他 progress が混入していても検出できない。さらに「プロンプト例示どおり」の変種が F4 の Stage2 成果として決勝資料まで繰り上がっており、壺師の生成関与が蟲師の成果に無記名で混ざる(必要エージェント構成の測定 §13-2 も汚染)。蟲師1機のやり直し時に同一タスクの再発行も不可能(RT1-OPS-5 と連鎖)。
- 最小修正案: §12 に1行追加——「task_XX.md は実ファイルとして壺ディレクトリに書いてから蟲師に渡す。『使い捨て』は次Stageが読まない、の意味であり削除しない」。progress テンプレ冒頭に「参照: task_XX.md」欄を必須化。

### RT1-OPS-2 [歪] Stage2ゲートは所有者も基準も未固定 — 法が蟲師ごとに割れ、割れたまま殺している
- 指摘: 憲法は関所/算盤を「課」の仕事とし(§2)、Stage2 を「軽い足切り(関所・算盤の pass/fail だけ)」(§7)とするが、pass/fail の基準と判定主体をどの成果物にも固定していない。実走では生成した本人(蟲師A/B/C)が課を兼ねて判定し、法が割れた。
- 根拠: progress_stage2_A.md「算盤: fail(理由: …回転が概算20〜25人/時にとどまる…)」vs progress_stage2_B.md「概算10〜12人/時にとどまる(**fail理由ではなく実数として明記**)」。state.md 測定メモ4「(A=fail / B・C=実数記録)」。さらに progress_stage2_integration.md はキルログで「暗幕迷宮…かつ**算盤fail**(回転20-25/h頭打ち)」を死因に引きつつ、脱出ゲームを「算盤が最弱(10-12/h)…回転劣位で落とす」と壺師が事後に再ゲートしている。
- 攻撃シナリオ: 20-25/h が fail で 10-12/h が pass という客観順序の逆転が現に起きた。生死が「どの蟲師に引かれたか」の籤で決まるなら、三原則1(相対評価)の前提=同一の法の下での喰い合いが壺内で崩れる。本番規模(蟲師5×20匹)では割れ幅が拡大し、壺師が異なる法の判定を横断比較してキルする構造誤りが常態化する。state.md の自己修正案(「回転弱=failにせず実数記録」を1行)は今回の1事例への対症で、「各Stageのゲート法を誰がどこに固定するか」という類の欠陥を塞がない。
- 最小修正案: §7 の Stage 表に1行追加——「各Stageのゲート仕様(pass/fail 基準)は壺師が Stage 開始前に task / shared_context 側へ明文固定し、判定者はその基準を引用して判定する」。判定テンプレに「適用基準の引用」欄を必須化し、基準を引用しない fail は壺師が採用前に差し戻す。

### RT1-OPS-3 [歪] 「モデル非依存」の型が配役をモデル名で焼き付け、実走はモデル無記名
- 指摘: §6 見出しは「パイプライン(モデル非依存)」だが、§1・§2 は壺師=Opus/蟲師=Sonnet を「不変」の憲法に焼き付け、測定対象自体を「Sonnetの最小判断単位」とモデル名で定義する。一方、実走成果物にはどの役をどのモデルが担ったかの実行記録が一切ない。
- 根拠: rules.md §2「配役(愛称・**不変**)…壺師|Opus…蟲師|Sonnet」、§1「測るのは、**Sonnetの最小判断単位**」、§6「パイプライン(モデル非依存)」、§10「`state.md`…ラウンド/**モデルを跨ぐ**受け渡し」。pot_A 全ファイルでモデル名の出現は state.md 測定メモ2 の結論文「律速は…Opus壺師の濃縮帯域」のみ(主張であって記録ではない)。
- 攻撃シナリオ: state.md はモデルを「跨ぐ」受け渡しを契約しながら、跨いだ事実を書く欄がない。メインモデルが切り替わった瞬間(モデル名の改称・世代交代は確実に起きる)、「R1 の測定結論(最小判断単位・必要並列数・濃縮帯域律速)はどのモデルの性質だったか」に答えられず、R2 以降との比較不能=5ラウンド累積の測定価値が崩れる。「基本的に更新しない」(§0)憲法にモデル名を書いた時点で、憲法自体に腐敗時限が仕込まれている。
- 最小修正案: §2 の表のモデル名を役割要件(分解・濃縮系 / 軽量並列系)に置換し、実バインドは壺ごとに state.md 冒頭の「配役バインド: 壺師=<model> / 蟲師=<model>」欄で宣言。progress・state の各テンプレに実行モデルのスタンプ1行を必須化。

### RT1-OPS-4 [歪] 「計5ラウンド」が未定義のまま、実走はその崖の手前で停止中
- 指摘: §11「勝ち抜け決定後、同手順で計5ラウンド」の「ラウンド」が無定義——R2 の入力(勝者を起点に何を生成するか)、勝者の扱い(シード再入場か殿堂入りか・再キルされ得るのか)、ラウンドごとの代表と §5「各壺は代表1匹を出す」の整合、いずれも書かれていない。pot_A は「R1 / 5」の Stage4 待ちで、勝ち抜け決定の次の一手が仕様上実行不能。
- 根拠: rules.md §11「勝ち抜け決定後、同手順で **計5ラウンド**。」(定義はこの1行のみ)、§6「↓ 勝ち抜けを起点に、同手順で次ラウンド ×5」、§5「各壺 = 地区大会:独立プロジェクトで完結し、**代表1匹を出す**」、state.md「ラウンド: R1 / 5」。§14 保留「中断中の5ラウンド(コワーク事業設計)を、この型のどこに接続するか」は、この数字が別文脈からの持ち込みである示唆。
- 攻撃シナリオ: 省吾が代表を選んだ直後、壺師は「同手順」を再開できない。R1 勝者を R2 の壺に入れれば勝者が被り畳みで消え得る(勝ち抜けの意味が消滅)、入れなければ R1〜R5 で代表5匹が積み上がり §5 の「代表1匹」と矛盾する。どちらに倒すかが運用者の即興になり、即興は乖離の量産機——5ラウンド分の state 連結(§10 の受け渡し契約)が運用者ごとに別物になる。
- 最小修正案: §11 に定義を追記して二択のどちらかに倒す——(案a)「ラウンド=同一壺での漏斗1周。R(n) の入力=新規生成+R(n-1) 代表(シード再入場・被り畳みの吸収先にしない)。壺の最終代表=R5 生存の1匹」/(案b)「1壺=1ラウンドで完結し、5ラウンド=壺5個。壺代表5匹が壺代表戦へ」。あわせて state.md テンプレに「R(n)代表」欄を追加。

### RT1-OPS-5 [軋] 蟲師/課のクラッシュ・部分完了Stageの再開規定ゼロ — state.md はStage境界でしか真実を持たない
- 指摘: 憲法にクラッシュ・タイムアウト・再試行の語が一つもなく、state.md の更新粒度は「各Stage終了で」(§10)のみ。途中 Stage(例:蟲師5機中3機だけ progress を書いた状態)で落ちた場合の再開手順が未定義で、§10 の「state.md があればそこから再開」は Stage 境界以外で機能しない。
- 根拠: rules.md §10「各Stage終了で `state.md` を更新」「`state.md` があればそこから再開」(失敗・再開系の規定は全文でここのみ。grep で確認)。実走のコミット履歴も蟲師 progress が2波(01/03/04 → 02/05)で着弾しており、途中死のウィンドウは現実に存在する。
- 攻撃シナリオ: Stage1 で 3/5 完了時にセッション死 → 新セッションは state.md から「Stage1 へ」しか読めず、5機を再起動する。既存 progress_stage1_01..03 を上書きすれば24匹分の生成が消えて母数40の監査が狂い、残せば別走行のバッチが混ざる——重複KILLは「**自分のバッチ内**の既出」(shared_context.md)にしか効かないため、走行を跨いだ被りが triage を素通りし、壺師の「40生成→27通過」統計が偽になる(漏斗の静かな崩壊)。Stage3 でも課エージェント1機(例:F4)だけの再発行規定がなく、task 実体がない(RT1-OPS-1)ため同一条件の再走もできない。
- 最小修正案: state.md テンプレに Stage マニフェスト(期待 progress ファイル一覧+着弾状況+ in_flight フラグ)を追加し、§10 の再開手順を「マニフェストの欠落分のみ、保存済み task_XX.md から再発行。走行を跨いだバッチ混在は禁止」と1段具体化。

### RT1-OPS-6 [軋] state.md の書き手が §6 と §12 で食い違い、同一壺への複数セッション並走に排他規定がない
- 指摘: §6 は state.md 更新を[省吾 舌]の工程に置き、§12 は壺師の仕事とする(実走は壺師が毎ステージ更新)。加えて「複数壺の並走」を推奨しながら、同一壺に2セッションが触れた場合のロック・セッションID・単一書き手の明文規定がなく、§10 の「state.md を探す」も多壺リポジトリでどれを拾うか未規定。
- 根拠: rules.md §6「[省吾 舌] 勝ち抜け決定 … └ state.md 更新(生存リスト + キルログ)」vs §12「壺師(メイン)は progress を全部読み、…`state.md` を更新して省吾に上げる」。§12「複数壺の並走:壺ごとにディレクトリを分ける…各壺は独立」(壺内の排他は無規定)。
- 攻撃シナリオ: 舌の裁定がどの経路で state.md に入るか(舌が書く/壺師が代筆)が未定義のため、Stage4 境界で更新が二重化・欠落し得る。また再開挙動が無条件「そこから再開」なので、同一壺を2セッションが開くと両方が蟲師バッチを起動して二重コスト+progress 衝突、最後に書いた側の state.md が勝ち、他方のキルログ差分が無音で消える——三原則2「敗者は毒になる」の毒=この型の主資産のロスト。
- 最小修正案: §10 の state.md 行に「書き手は壺師のみ(舌の裁定は壺師が代筆記録)」と明記し §6 の図を合わせる。state.md 冒頭に session_id / in_flight リース欄を持たせ、起動時挙動に「リースが生きた壺には触らない」を1行追加。

### RT1-OPS-7 [軋] 「読み取り専用」の shared_context に、型が自認した修正の置き場がない(版管理不在)
- 指摘: 型自身が出した改善(ゲート基準を shared_context に1行固定)は壺の途中で shared_context を書き換えることを要求するが、§10 はこれを「壺ごと・読み取り専用」と定義するだけで、改訂の権限・タイミング・版記録のプロトコルがない。progress 側にも「どの版の法で走ったか」を残す欄がない。
- 根拠: rules.md §10「`shared_context.md`|壺ごと・読み取り専用|蟲師全機に配る壺の定義」。state.md 測定メモ4「pass/fail基準を shared_context に1行固定すべき」。pot_A/shared_context.md に版・改訂欄なし。progress_* はいずれも参照版を記録していない。
- 攻撃シナリオ: R2 でゲート1行を追記した瞬間、Stage1 生存者(旧法で triage)と Stage2 判定(新法)が別の法の下の結果になるが、その事実はどこにも記録されず、「この蟲はどの基準で生き残ったか」を後から復元できない。RT1-OPS-1(タスク無記録)と合わさると、壺の全判定が「そのとき配られた何か」への信仰になる。
- 最小修正案: shared_context テンプレに version と改訂履歴(1行/回)を追加し、「改訂は壺師のみ・Stage境界のみ」を §10 に1行追記。progress テンプレ冒頭の参照欄(RT1-OPS-1 の修正)に「shared_context v◯」を含める。

### RT1-OPS-8 [軋] Stage1「セットごとに続行/打ち切りを判断」の主体・基準・記録先が無規定(実走にも痕跡なし)
- 指摘: §11 Stage1 の「20匹単位で生成し、セットごとに続行/打ち切りを判断…倍率分くり返す」は、誰が・何を見て・どこに記録して判断するのか未定義。pot_A にはこの判断の痕跡が一切なく(8匹×5機の一括)、縮小版とはいえ制御ループが最初から不履行。
- 根拠: rules.md §11「Stage1 生成→一次選別:20匹単位で生成し、セットごとに続行/打ち切りを判断。客観三値で足切り。倍率分くり返す」。pot_A の progress_stage1_* / integration / state.md のどこにも続行/打ち切りの記録なし。
- 攻撃シナリオ: 本番規模(100匹〜)では「くり返す」回数が実質未管理になり、生成母数が成果物から復元できない。§13-2 の測定(必要エージェント数・並列規模)は分母不明のまま結論だけが state.md に残る——測定治具としての壺が、自分の実験回数を数えられない。打ち切りが壺師の胸三寸なら、通過率の低いレンズ(今回の食=3/8)を続けるか切るかで漏斗の形が黙って変わる。
- 最小修正案: §11 に「続行/打ち切りは壺師が判断し、state.md にセット番号・通過率・判定を1行ずつ記録。縮小運用でもバッチ=セットとして同じ記録を残す」と追記。
